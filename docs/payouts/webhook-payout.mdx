Bitnob notifies your server as a payout advances, so you can update records and notify users without polling. Set the destination with `callback_url` when you [initialize a payout](/api-reference/payouts/initialize-payout), or configure a global webhook URL on your dashboard.

Before handling payout events, have the shared plumbing in place from [Webhooks](/api-reference/payouts/webhooks): verify the `x-bitnob-signature` HMAC on every delivery, return `200` quickly, and expect retries, which means the same event can arrive more than once. De-duplicate on `event_id`.

## The four events

| Event | Fires when | Act on it |
|---|---|---|
| `payouts.initialized` | Payout accepted against a quote. Nothing settled. | Mark as in flight. |
| `payouts.processing` | The settlement rail picked it up. Not yet delivered. | Show progress. |
| `payouts.withdrawal.success` | Funds delivered to the beneficiary. | Credit the order, notify the user. |
| `payouts.withdrawal.expired` | Quote expired unfunded. Nothing settled. | Re-quote to retry. |

This is the complete catalogue. There is no failure event: a `FAILED` payout is detected by polling [Get payout](/api-reference/payouts/get-payout), so run a reconciliation sweep alongside your webhook handler. The status vocabularies are compared on [Statuses and webhook events](/docs/payouts/statuses-and-webhook-events).

<Note>
  `data.status` in a payout webhook is the lowercase event outcome (`initiated`, `processing`, `success`, `expired`). It is not the payout record's uppercase lifecycle status. Route on the `event` field.
</Note>

## Payloads

Every event carries the payout record, so field names match the payouts API responses. Use `reference` to match events to your own records. On `payouts.withdrawal.success`, `completed_at` is when settlement finished; act on this event when crediting an order. On `payouts.withdrawal.expired`, nothing settled; create a fresh quote to retry.

## Handler checklist

- Verify the signature before parsing anything else; see [Verifying events](/api-reference/payouts/webhooks#verifying-events).
- Return `200` immediately and process asynchronously. Bitnob retries non-200 deliveries 3 times after the first failure.
- Make the handler idempotent on `event_id`.
- Confirm terminal state with [Get payout](/api-reference/payouts/get-payout) before releasing goods or services; do not act on a webhook alone.
