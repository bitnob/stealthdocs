<Note>
  This page covers **Platform**, the non-custodial product. The custodial Bitnob API used for payouts, cards, and trading signs requests with HMAC instead. See [API authentication](/api-reference/authentication/authentication).
</Note>

Every request to the Platform API is authenticated with an API key. Keys are issued from the Bitnob dashboard and carry a permission set that is bound to your organisation at issue time.

## Base URL

```
https://api.platform.bitnob.com
```

## Send your API key

Pass your key on the `X-API-Key` header with every request. To confirm a key works, call [Get API Key Info](/api-reference/platform/meta/get-api-key-info). A 200 means the key is valid, and the response lists the organisation and granted scopes:

```http
POST /wallets HTTP/1.1
X-API-Key: <your_api_key>
Content-Type: application/json
```

The organisation context is resolved automatically from the key. You never need to send an org ID header.

<Warning>
  Keep keys server-side. Never expose a Platform API key in a mobile app, frontend JavaScript bundle, or public repository. A leaked key grants the same authority a signed-in admin user does, up to the limits of its permission set and configured policies. All signing should happen in your backend.
</Warning>

## Required headers

| Header | Required | Description |
|---|---|---|
| `X-API-Key` | Yes | Your API key. Organisation is derived from the key automatically. |
| `X-API-VERSION` | No | API version. Defaults to `v1` if not supplied. |
| `Content-Type` | For writes | Must be `application/json` for all POST, PUT, and PATCH requests. |

## How authorization works

API key calls never receive a WebAuthn or MFA challenge. When the key has the required permission and the request passes every configured policy, the Bitnob Secure Enclave signs synchronously.

The authorization flow for every transaction is:

1. **API key is verified.** The key must exist, be active, and carry the permission required for the requested operation: inspect scopes on [Get API Key Info](/api-reference/platform/meta/get-api-key-info) to check.
2. **Policies are evaluated.** Every active policy is checked against the transaction parameters, spending limits, address whitelists, velocity caps, and approval thresholds all run before signing.
3. **Enclave signs or holds.** If every policy passes, the Enclave signs immediately. If a policy fires `require_approval`, the transaction is held in `pending_authorization` until approvers vote.
4. **Transaction is broadcast.** After signing, the transaction is broadcast to the network. If gas sponsorship is needed, the gas station tops up the wallet first.

A leaked key cannot exfiltrate funds beyond what its policies permit. Spending limits, address whitelists, velocity caps, and approval quorums all enforce constraints independently of the key's permission set.

## API versioning

The Platform API supports two versioning strategies. Both are valid and can be used interchangeably.

**Header-based (recommended)**

```http
GET /wallets HTTP/1.1
X-API-VERSION: v1
X-API-Key: <your_api_key>
```

**Path-based**

```http
GET /v1/wallets HTTP/1.1
X-API-Key: <your_api_key>
```

Routes in the API reference are shown without a version prefix. Prepend `/v1/` or set the `X-API-VERSION: v1` header as needed.

## Errors

Platform returns a nested `error` object. This differs from the Bitnob API, which uses a flat RFC 7807 body, so do not share one error handler between the two products.

```json
{
  "error": {
    "type": "authentication_error",
    "code": "not_authenticated",
    "message": "X-API-Key header is required"
  }
}
```

| Field | Use |
|---|---|
| `error.type` | The error class, for example `authentication_error` or `not_found_error`. |
| `error.code` | The stable machine-readable code. Branch on this. |
| `error.message` | A human-readable explanation. Do not parse it. |

Common authentication codes:

| Code | Meaning |
|---|---|
| `not_authenticated` | The `X-API-Key` header is missing, or the key format is invalid. |
| `route_not_found` | The endpoint does not exist. Check the path and the version prefix. |

## Idempotency

All mutation endpoints that create resources (vaults, [wallets](/api-reference/platform/wallets/create-wallet), [transactions](/api-reference/platform/transactions/create-transaction)) require an `idempotency_key` in the request body. This is a client-generated string of 1–64 characters that identifies the request uniquely.

- If a request succeeds, resubmitting the same `idempotency_key` returns the original result without re-executing.
- If the original request is still in-flight, resubmitting returns `409 Conflict`.
- Use UUIDs or a composite key (e.g. `withdrawal-cust12345-001`) to ensure global uniqueness.

<Tip>
  Always include an `idempotency_key` so you can safely retry a timed-out request without risk of creating duplicate transactions.
</Tip>
