A complete walkthrough for building a production exchange on top of Bitnob Enterprise, from customer onboarding to policy-governed withdrawals.

This guide covers the full integration lifecycle: creating the vault topology, onboarding customers, detecting deposits, setting up gas sponsorship, processing withdrawals, and locking down the system with layered policies.

<Note>
  You need a Bitnob Enterprise API key with admin permissions. All requests use the `X-API-Key` header. See [Authentication](/docs/enterprise/authentication) for details.
</Note>

## Step 1: Create a pool vault

Create one pool vault per chain your exchange supports. A pool vault holds unlimited wallets, which makes it the correct choice for assigning a dedicated deposit wallet to each customer. See [Vaults](/api-reference/wallet-infrastructure/vaults/list-vaults) for the vault model, and [List Vaults](/api-reference/wallet-infrastructure/vaults/list-vaults) to enumerate the ones you have created.

```http
POST /vaults
Content-Type: application/json
X-API-Key: <api_key>

{
  "name": "Ethereum Deposit Pool",
  "vault_type": "pool",
  "idempotency_key": "eth-pool-init-001"
}
```

```json
{
  "success": true,
  "data": {
    "id": "vault_eth_001",
    "name": "Ethereum Deposit Pool",
    "vault_type": "pool",
    "status": "active",
    "wallet_count": 0
  }
}
```

Repeat this for each chain you support, Bitcoin, Solana, Tron, Base, and so on. Which chains are available is returned by [List Chains](/api-reference/wallet-infrastructure/assets/list-chains). Store the vault `id` for each chain, [Get Vault](/api-reference/wallet-infrastructure/vaults/get-vault) reads one back, you will use it in the next step.

## Step 2: Onboard customers

For each customer, [create a wallet](/api-reference/wallet-infrastructure/wallets/create-wallet) inside the pool vault using `customer_ref_id` to link it to your internal customer ID. The response includes pre-derived deposit addresses for every asset you specify. You can also [list](/api-reference/wallet-infrastructure/wallets/list-addresses) or [add](/api-reference/wallet-infrastructure/wallets/create-address) addresses later.

```http
POST /vaults/:vault_id/wallets
Content-Type: application/json
X-API-Key: <api_key>

{
  "name": "Customer 12345 - ETH",
  "chain": "ethereum",
  "customer_ref_id": "cust_12345",
  "wallet_type": "hot",
  "asset_ids": ["ETH", "USDC_ETH", "USDT_ETH"],
  "network": "mainnet",
  "idempotency_key": "cust-12345-eth-001"
}
```

```json
{
  "success": true,
  "data": {
    "id": "wallet_abc123",
    "vault_type": "pool",
    "customer_ref_id": "cust_12345",
    "chain": "ethereum",
    "wallet_type": "hot",
    "status": "active",
    "primary_addresses": [
      {
        "chain": "ethereum",
        "address": "0x742d35Cc...",
        "network": "mainnet"
      }
    ]
  }
}
```

Show the customer their deposit address from `primary_addresses`. Store the wallet `id` in your database mapped to the customer's account.

## Step 3: Detect deposits

Poll for inbound transactions with [List Transactions](/api-reference/wallet-infrastructure/transactions/list-transactions), or use [Subscriptions](/api-reference/wallet-infrastructure/subscriptions/list-subscriptions) to receive real-time notifications for each deposit.

```http
GET /transactions
  ?wallet_id=<wallet_id>
  &direction=inbound
  &status=completed
  &period=24h
X-API-Key: <api_key>
```

```json
{
  "success": true,
  "data": [
    {
      "id": "tx_xyz789",
      "direction": "inbound",
      "status": "completed",
      "asset_symbol": "USDC",
      "amount_decimal": "250.00",
      "from_address": "0xabc...",
      "to_address": "0x742d35Cc...",
      "confirmations": 12,
      "confirmed_at": "2026-05-12T09:43:21Z"
    }
  ]
}
```

Credit the customer's exchange balance when a deposit reaches `completed` status with sufficient confirmations. Always reconcile against `amount_decimal` and `asset_symbol`: do not rely on internal accounting alone.

<Tip>
  For production, subscribe to `incoming_token_tx` and `confirmation_threshold_met` events with [Create Subscription](/api-reference/wallet-infrastructure/subscriptions/create-subscription) instead of polling. Delivery can be audited with [List Delivery Events](/api-reference/wallet-infrastructure/subscriptions/list-subscription-delivery-events).

  ```http
  POST /subscriptions
  Content-Type: application/json
  X-API-Key: <api_key>

  {
    "address": "0x742d35Cc...",
    "chain": "ethereum",
    "network": "mainnet",
    "event_type": "incoming_token_tx",
    "webhook_url": "https://exchange.example.com/webhooks/bitnob",
    "label": "Customer deposit monitor"
  }
  ```
</Tip>

## Step 4: Set up gas stations

[Create one gas station](/api-reference/wallet-infrastructure/gas-stations/create-gas-station) per chain to sponsor withdrawal fees automatically. Without a gas station, your customers would need to hold native tokens (ETH, TRX, SOL, etc.) alongside their assets.

```http
POST /gasstations
Content-Type: application/json
X-API-Key: <api_key>

{
  "name": "ETH Gas Station",
  "chain": "ethereum",
  "network": "mainnet",
  "threshold": "0.5",
  "auto_refill_enabled": true,
  "refill_amount": "1.0",
  "refill_from_wallet_id": "<treasury_wallet_id>"
}
```

<Note>
  **Tron: stake TRX for energy.** On Tron, USDT transfers consume energy instead of TRX. Stake TRX from your gas station to get energy units. This dramatically reduces the per-transfer cost.

  ```http
  POST /gasstations/:id/stake
  Content-Type: application/json
  X-API-Key: <api_key>

  {
    "amount": "10000",
    "resource": "ENERGY"
  }
  ```
</Note>

Monitor gas station health with `GET /gasstations/stats`, or read a single station with [Get Gas Station](/api-reference/wallet-infrastructure/gas-stations/get-gas-station). Set up alerting when `health_status` is `low`, and top up with [Refill Gas Station](/api-reference/wallet-infrastructure/gas-stations/refill-gas-station).

## Step 5: Process withdrawals

When a customer requests a withdrawal, [create a transaction](/api-reference/wallet-infrastructure/transactions/create-transaction) with gas sponsorship enabled: see [Sponsor and Broadcast](/api-reference/wallet-infrastructure/gas-stations/sponsor-and-broadcast-external-tron-transaction). As long as every configured policy passes, the transaction is signed by the Enclave and broadcast automatically.

```http
POST /transactions
Content-Type: application/json
X-API-Key: <api_key>

{
  "wallet_id": "<customer_wallet_id>",
  "to_address": "0x742d35Cc6634C0532925a3b844Bc9e7595f1B8A1",
  "amount": "100.0",
  "asset_id": "USDC_ETH",
  "network": "mainnet",
  "fee_level": "medium",
  "sponsor_gas": true,
  "idempotency_key": "withdrawal-cust12345-001"
}
```

```json
{
  "success": true,
  "data": {
    "id": "tx_wd001",
    "status": "signed",
    "amount_decimal": "100.0",
    "asset_symbol": "USDC",
    "sponsored": true,
    "to_address": "0x742d35Cc..."
  }
}
```

If a policy requires multi-party approval, the response status will be `pending_authorization` instead of `signed`. Always wait for `completed` status, confirmed via a [subscription](/api-reference/wallet-infrastructure/subscriptions/create-subscription) or by polling [Get Transaction](/api-reference/wallet-infrastructure/transactions/get-transaction), before crediting or debiting exchange balances.

## Step 6: Configure policy layers

Build a layered policy stack for defense in depth. Policies are evaluated in priority order. Higher numbers are evaluated first.

**Layer 1. Root quorum.** Protect policy changes themselves. Without this, any admin key can modify policies unilaterally.

```http
POST /policies/quorum
Content-Type: application/json

{
  "name": "Exchange Admin Quorum",
  "description": "2-of-3 admins must approve policy changes",
  "rules": [{
    "name": "Dual admin approval",
    "action_type": "require_approval",
    "conditions": [
      {
        "field": "operation",
        "operator": "in",
        "value": "policy.*,quorum.*"
      }
    ],
    "action_config": { "required_approvals": 2 }
  }]
}
```

**Layer 2. Block large withdrawals.** Reject anything over \$50,000 outright.

```http
POST /policies
Content-Type: application/json

{
  "name": "Block large withdrawals",
  "category": "limits",
  "priority": 200,
  "rules": [{
    "name": "Block over $50K",
    "action_type": "block",
    "conditions": [
      {
        "field": "amount_usd",
        "operator": "gt",
        "value": "50000"
      }
    ]
  }]
}
```

**Layer 3, velocity limits.** Cap each wallet at \$100,000 per day; anything above needs an approval.

```http
POST /policies
Content-Type: application/json

{
  "name": "Daily velocity limit",
  "category": "velocity",
  "priority": 150,
  "rules": [{
    "name": "$100K daily cap",
    "action_type": "require_approval",
    "conditions": [
      {
        "field": "daily_volume_usd",
        "operator": "gt",
        "value": "100000"
      }
    ],
    "action_config": { "required_approvals": 1 }
  }]
}
```

## Step 7: Populate the address book

Add known safe addresses (exchange hot wallets, partner addresses, institutional counterparties), to the address book. Then create a `whitelist` category policy to block transfers to any non-listed destination. Address book entries are immutable and validated against their chain at creation; see [Core concepts](/docs/enterprise/core-concepts#address-book).

```http
POST /addressbook
Content-Type: application/json

{
  "name": "Binance Hot Wallet",
  "chain": "ethereum",
  "network": "mainnet",
  "address": "0x28C6c06298d514Db089934071355E5743bf21d60",
  "notes": "Binance main hot wallet"
}
```

```http
POST /policies
Content-Type: application/json

{
  "name": "Whitelist-only withdrawals",
  "category": "whitelist",
  "priority": 300,
  "rules": [{
    "name": "Block non-whitelisted destinations",
    "action_type": "block",
    "conditions": [
      {
        "field": "to_address",
        "operator": "not_in",
        "value": "addressbook"
      }
    ]
  }]
}
```

## Step 8: Monitor and export

Use these endpoints to power your operational dashboards and run daily reconciliation. The documented reads are [List Transactions](/api-reference/wallet-infrastructure/transactions/list-transactions), [List Gas Stations](/api-reference/wallet-infrastructure/gas-stations/list-gas-stations), and [List Delivery Events](/api-reference/wallet-infrastructure/subscriptions/list-subscription-delivery-events) for notification health.

```http
# Gas station health
GET /gasstations/stats

# Policy coverage
GET /policies/stats

# Transaction analytics
GET /transactions/analytics
```

```http
GET /transactions/export
  ?wallet_id=<id>
  &from_date=2026-05-01T00:00:00Z
  &to_date=2026-05-12T23:59:59Z
  &format=csv
X-API-Key: <api_key>
```

Run daily reconciliation by matching your internal ledger against the exported transaction history. Investigate any withdrawal that was initiated but lacks a final `completed` status within your expected settlement window.

- Match `idempotency_key` against your internal withdrawal records.
- Verify `amount_decimal` and `asset_symbol` against customer ledger entries.
- Alert on any transaction stuck in `pending_authorization` beyond your SLA window: confirm state with [Get Transaction](/api-reference/wallet-infrastructure/transactions/get-transaction).
- Track gas station health daily and [refill](/api-reference/wallet-infrastructure/gas-stations/refill-gas-station) before `health_status` reaches `low`.
- Retry any failed notification with [Retry Delivery Event](/api-reference/wallet-infrastructure/subscriptions/retry-subscription-delivery).
