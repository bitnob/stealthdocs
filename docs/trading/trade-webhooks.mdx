The order response returns immediately, but the outcome arrives as a webhook. Update balances and mark trades settled on `trade.completed`; surface and route failures on `trade.failed`.

| Event | Fires when | Act on it |
|---|---|---|
| `trade.completed` | The trade executed and settled. | Credit your ledger, show success. |
| `trade.failed` | The trade failed: quote expiry, balance, or system error. | Unlock any UI hold, show the reason, offer a re-quote. |

Deliveries are HTTPS POSTs from the addresses listed under [Source IPs](/api-reference/webhooks#source-ips). Each one carries an `x-bitnob-signature` header: an HMAC SHA-512 of the raw request body, keyed with your webhook secret. Verify it before you parse the body, comparing in constant time, as shown in [Verifying events](/docs/stablecoins/address-webhook-events).

## Payloads

<CodeGroup>

```json trade.completed
{
  "event": "trade.completed",
  "event_id": "944a4089-6065-49ca-8f43-fb10f15c59e6",
  "data": {
    "tradeId": "trd_0a9eab21",
    "reference": "trade_order_4837",
    "from": "usdt",
    "to": "bitcoin",
    "inputAmount": 10000,
    "outputAmount": 225000,
    "rate": 2250,
    "walletId": "wallet_btc_3488",
    "status": "completed",
    "timestamp": "2025-05-16T10:13:45Z"
  }
}
```

```json trade.failed
{
  "event": "trade.failed",
  "event_id": "944a4089-6065-49ca-8f43-fb10f15c59e6",
  "data": {
    "tradeId": null,
    "reference": "trade_order_4837",
    "from": "bitcoin",
    "to": "usdt",
    "inputAmount": 500000,
    "reason": "Quote expired",
    "status": "failed",
    "timestamp": "2025-05-16T10:16:22Z"
  }
}
```

</CodeGroup>

`reference` is your join key back to the order you submitted; `reason` on failures carries the cause, for example `Quote expired` or `Insufficient balance`.

## Delivery, retries and ordering

- Return a `200` as soon as the signature checks out, then process. A slow handler times out, and a timeout counts as a failed delivery.
- A non-`200` response is retried up to 3 more times with exponential backoff. After that, delivery stops.
- The same event can arrive more than once. De-duplicate on `event_id`.
- Events can arrive in any order, because a retried delivery may land after a later one. Each trade ends in exactly one terminal event: `trade.completed` or `trade.failed`.
- Retries are finite, so an endpoint that is down for long enough misses events for good. Reconcile anything you still hold as pending with [Get order](/api-reference/trading/get-order-by-id-or-reference).

## Handler checklist

- Match `reference` against your ledger before mutating anything.
- Log every event with delivery timestamp and processing outcome.
- Reconcile on a schedule, so a missed delivery never strands a trade as pending. [List orders](/api-reference/trading/list-orders) returns crypto-pair orders only; fetch NGN orders one at a time with [Get order](/api-reference/trading/get-order-by-id-or-reference).
- Alert internally when `trade.failed` volume spikes; a burst usually means a systemic cause, not user error.
