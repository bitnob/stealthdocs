Cards are prepaid, so they hold nothing beyond what you load. A top-up is debited from your company balance, together with its fee. If that balance can't cover both, the call fails, and the error's `extensions.currency` names the balance that was checked.

## Check before you fund

| Constraint | Value |
|---|---|
| Minimum per top-up | \$2. Less fails with `400` "amount below minimum funding of \$2". |
| Maximum per transaction | \$2,500 |
| Maximum card balance | \$50,000 |
| Card status | Must be `active`. Frozen and terminated cards cannot be funded. |
| Source balance | Must cover the amount plus the fee: a \$2.00 top-up needs \$3.00. |

Funding fees are on [Fees and decline rules](/docs/card-issuing/card-fees): \$1 flat below \$100, 1% at \$100 and above.

## Make the call

Full schema: [Fund or withdraw balance](/api-reference/cards/fund-or-withdraw-balance). Amounts are micro-units, 1 USD = 1,000,000.

```http
POST /api/cards/{cardId}/balance
```

```json
{
  "amount": 2000000,
  "reference": "FUND_TYU039847383",
  "type": "fund"
}
```

<ParamField body="amount" type="integer" required>
  The amount to move, in micro-units of the card currency. `2000000` is \$2.00.
</ParamField>

<ParamField body="type" type="string" required>
  `fund` credits the card from your balance. `withdraw` reverses direction and returns card balance to your account.
</ParamField>

<ParamField body="reference" type="string" required>
  Your unique identifier for this operation, and its idempotency key: retrying with the same reference returns the original transaction instead of creating a duplicate.
</ParamField>

## Confirm with the webhook

`virtualcard.topup.completed` confirms the load; do not treat the HTTP response alone as success.

```json
{
  "eventId": "c28f4b7a-9c6d-4e0f-a3a4-6c7d8e9f0a1b",
  "companyId": "1e340e84-f42e-4b11-b241-4d0c10c28e33",
  "event": "virtualcard.topup.completed",
  "data": {
    "cardId": "f7e37478-6569-4979-92d2-1a46d9c8e33d",
    "id": "0464f449-dbbf-4f1a-bedf-e78e0cd78e0e",
    "amount": 3000000,
    "reference": "FUND_WITH_IS870100180800301200300078",
    "narrative": "card_topup_3_usd",
    "status": "completed",
    "initiatedFrom": "wallet",
    "isTerminated": false
  }
}
```

A failed load arrives as `virtualcard.topup.failed` with the same shape and `status: "failed"`.

## When funding fails

<AccordionGroup>
  <Accordion title="Insufficient balance (400)">
    Your company balance can't cover the amount plus fee. The error carries `extensions.error_code: "COMPANY_INSUFFICIENT_BALANCE"`, the `currency` of the balance that was checked, and the `required` and `available` amounts. Top up that balance, then retry.
  </Accordion>
  <Accordion title="Amount below the minimum (400)">
    Top-ups start at \$2.00 (`2000000`). The error reads "amount below minimum funding of \$2".
  </Accordion>
  <Accordion title="Card is frozen or terminated (403)">
    Only `active` cards can be funded. Check status with [Get card](/api-reference/cards/get-card) first, and [unfreeze](/api-reference/cards/freeze-or-unfreeze) if appropriate.
  </Accordion>
</AccordionGroup>

## Withdraw from a card

Send `type: "withdraw"` to move card balance back to your company balance. Withdrawals carry no fee, and appear in your ledger as a `CARD_WITHDRAWAL` credit.

```json
{
  "type": "withdraw",
  "amount": 1000000,
  "reference": "WITHDRAW_7c1e9f42"
}
```

Each card allows one withdrawal every 300 seconds. A second one inside that window fails with `400` "rate limit exceeded: please wait 300 seconds before making another withdrawal".

## Funding patterns

| Pattern | When it fits |
|---|---|
| On demand | The user taps "Top up" in your app and you fund immediately. |
| Auto-fund | You top up automatically when the card balance drops below a threshold. |
| Per event | You load the card right before a known spend, for example at payout time. |
| Recurring | Scheduled loads for allowances and spend programmes. |

All funding is platform-initiated through your API; cardholders cannot fund cards directly. Whatever the pattern, log the reference and fee of each load for reconciliation, and confirm each load from the webhook rather than assuming it.
